BOSTON CIRCULAR ECONOMY · DEVELOPER GUIDE

Patterns and Modular Code

Reuse the pattern the code already shows. Extend by subclassing a parent. Compose in a job or an entry file. Depend on the parent, never on a child.

A parent is an abstract base class. It fixes the shape of a part; a child fills in one case. Callers use the parent type, so a child can swap without caller changes. That swap point is an inversion of control seam — the ◆ markers in the architecture views.

Pattern names below come from their sources, not from this guide: GoF is Gamma, Helm, Johnson, and Vlissides, “Design Patterns” (1994). Repository is Fowler, “Patterns of Enterprise Application Architecture” (2002). Dependency Injection is Fowler (2004). Rows marked React idiom have no GoF name and get none.

UI PATTERNS — COMPOSITE · DECORATOR · STATE · OBSERVER (GOF) + REACT IDIOMS

The UI does not inherit — it composes

React gets its reuse from composition and hooks, not class parents.

Figure 7 — Anatomy of a screen. The provider supplies the client; the container owns the query; presentational cards render props; the URL carries shareable state.
PatternRule
Provider · React idiomOne typed API client, built at the entry, reaches every screen through context (◆3)
Container / presentational · React idiomA component that fetches is a container. A component that only renders takes props. Never both in one file
Custom hook · React idiomReusable logic sits in a hook, so screens stay thin and logic is testable alone
Composite · GoFA part-whole tree where parents and children share one interface: a question group holds its options the way a page holds its parts (#76)
Decorator · GoFA wrapper adds responsibilities around a component: DataState renders loading, error, and empty around the success view (#53)
Controlled component · Observer shape, GoFThe parent form owns the value; children update when the state changes and notifies them (#84)
URL as stateShareable state lives in the URL, not in a component (#75)
State · GoFThe flow alters its behavior when its state changes: the next step is a function of the answers so far (#76)

State lives at the lowest parent that needs it — the URL for shareable state, the form for form state, the hook for query state. Do not lift state to the app root by default.

THE RULES UNDER THE PATTERNS

SOLID, in its authors' words

Five class-design principles from Robert C. Martin, “Design Principles and Design Patterns” (2000); the acronym is Michael Feathers’. OCP is Bertrand Meyer’s; LSP is Barbara Liskov’s (1987).

S
Single Responsibility
“A class should have one, and only one, reason to change.”
Here: a class changes when its one source changes, or its one contract changes — never both.
O
Open / Closed
“Software entities should be open for extension, but closed for modification.”
Here: extend by adding a child. The pipeline and the callers do not change.
L
Liskov Substitution
“Objects should be replaceable with instances of their subtypes without altering the correctness of the program.”
Here: every store child stands in for LocalDataStore, in tests and in production.
I
Interface Segregation
“Clients should not be forced to depend on interfaces they do not use.”
Here: parents hold one to three methods. Public (#46) and internal (#47) contracts stay separate.
D
Dependency Inversion
“High-level modules should not depend on low-level modules; both should depend on abstractions.”
Here: seams ◆1 to ◆4. High-level code names parents; builders supply the concrete parts.

One honest limit: the jobs still wire each source by name (scrape_to_local.py builds each querier in turn). Open/Closed holds for the pipeline classes; the job file grows a few lines per source. A source registry closes that gap when a third source arrives — not before.

Change a contract field

A contract change touches both sides, so it has an owner and an order: propose the change to the contract owner (#46 API: Yuan · #75 search URL: Hubert) → change packages/contracts and the API schema in one pull request → update the ETL writer and the API reader → regenerate the client types from the API schema; never edit them by hand.

What not to do
  • Do not build a concrete store, querier, or client inside a handler, a page, or a rule. Build it in a job or an entry file, and pass the parent type in.
  • Do not add a field to a contract on one side only.
  • Do not put a business rule in a router or a page. Rules live in the business layer (View 5).
  • Do not add a dependency injection container. Constructor injection and FastAPI Depends cover every seam in this app.
